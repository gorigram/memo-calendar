# Cloud backend (standalone Cloudflare Worker)

The current public deployment is [ゴレンダー](https://memo-calendar-glass.maponaru0519.workers.dev), Worker version `8bf4f19c-697e-41a6-b2eb-1ab6df14c45e`, with D1 (`DB`) and Workers AI (`AI`) bindings configured. The current source has 78 passing Node tests; build, artifact validation, and diff checks pass. OAuth, event create/edit/delete, weekly recurrence sync, and AI-assisted title refinement were verified using a personal Google account. Existing Google Calendar events are fetched live for the visible week and displayed read-only; they are not copied into D1. Imported recurrence instances are expanded by Google Calendar. Production browser testing was limited to the creator's account. The site can run entirely from its local browser store. D1 event storage is partitioned per authenticated account: standalone mode uses its signed Google-linked session, while Sites identity is accepted only when explicitly enabled for that runtime. The Worker never uses a shared fallback identity: requests without a valid Sites identity or standalone signed session return `401`.

Source repository: [github.com/gorigram/memo-calendar](https://github.com/gorigram/memo-calendar).

Google OAuth consent is configured as `External / Testing`, and only the designated test user is authorized. In Google's testing mode, refresh tokens for scopes beyond basic profile access expire after seven days, so the user must reconnect. See [Google OAuth testing and refresh-token behavior](https://developers.google.com/identity/protocols/oauth2/) and [Google's test-user settings](https://support.google.com/cloud/answer/15549945?hl=en). The website and source repository are public, but Google sign-in is not open to the public. Before offering OAuth to general users, set Google-side publication settings, prepare a privacy policy and other required information, and meet the review requirements for the requested scopes. Domains and other assets should follow those requirements.

## Configure

1. For a new Cloudflare account, create a D1 database named `memo-calendar-glass` and put its ID in `wrangler.jsonc`. Apply schema changes with `pnpm exec wrangler d1 migrations apply memo-calendar-glass --remote`. The public D1 has additive migrations `0002_tasks.sql` and `0003_templates_batches.sql` applied. The first adds task fields while preserving existing schedules; the second adds account-scoped numbered templates and idempotency receipts for multi-event batches.
2. In Google Cloud Console, enable the Google Calendar API and create a **Web application** OAuth client. Register `https://<worker-host>/api/google/callback` as an authorized redirect URI. OAuth consent requests OpenID identity plus `calendar.events` access.
3. Set Worker secrets with `pnpm exec wrangler secret put GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`, `APP_SESSION_SECRET`, and `TOKEN_ENCRYPTION_KEY`. Generate the encryption key and session secret independently with at least 32 random bytes. Never commit real secrets or `.dev.vars`.
4. Deploy with `pnpm exec wrangler deploy`, then register the exact deployed app origin plus `/api/google/callback` as the OAuth redirect URI. `APP_ORIGIN` is set to the published Worker origin in `wrangler.jsonc`.

In the private Sites runtime, bind `DB` to D1 and set `TRUST_SITES_IDENTITY=true`; the Worker reads Sites' `oai-authenticated-user-id` header, which the private Sites dispatcher supplies. Never enable that setting on a public standalone Worker. Standalone Wrangler uses a Google account session cookie (`TRUST_SITES_IDENTITY=false`) and may be deployed independently. For the app preview use `pnpm dev`; it intentionally has no D1, Workers AI, or identity bindings. To test Cloudflare runtime bindings locally, use `pnpm exec wrangler dev` and add `.dev.vars` from `.dev.vars.example`; register the resulting local callback URI for the OAuth client if testing the full flow.

## API contract

- `GET /api/status`: returns storage, AI, signed-in state, and Google setup/connection status without exposing identity or token data. `accountKey` is a short hash used to partition client preferences; a Google Calendar grant is not required for authenticated D1 CRUD.
- `POST /api/parse` with `{text, timezone?}`: authenticated requests may use Workers AI to extract event details only after the deterministic parser has identified a date and start time. Anonymous requests never invoke AI; they use the deterministic parser. Missing start time is a clarification.
- `GET /api/events`, `POST /api/events`, `PUT /api/events/:id`, `DELETE /api/events/:id`: per-user event storage. A missing end time defaults to one hour after the explicit start. Send `autoSync:true` with create/update only after the user enables automatic Calendar addition; responses include a sync status and report partial failure explicitly.
- `POST /api/events/batch` with `{batchId,events:[...],autoSync}`: validates a schedule batch and stores it atomically for the authenticated account. Repeating a batch ID with the same content replays the stored result without duplicating events; the same ID with different content is rejected. Google sync reports each event's outcome so partial failures remain visible and can be safely retried.
- `GET /api/templates`, `PUT /api/templates` with `{templates:[{id,shortcut,title,time,durationMinutes,recurrence}]}`: reads or atomically replaces an account's memo templates. `shortcut` accepts a trimmed, NFKC-normalized single-line name of 1–40 characters; normalized names and IDs must be unique. Legacy `①`–`⑳` values remain readable and are exposed as a human-readable call name formed from the NFKC-normalized title (up to 30 codepoints) and `HH:mm`, with the original circled value in `aliases`; collisions get a deterministic `（2）`, `（3）` suffix while staying within the 40-character limit. Loading these rows does not rewrite D1. Guest templates stay in that browser's local storage.
- Schedule records retain explicit start/end time semantics. A task record uses `type:"task"`, requires a real `dueDate` in `YYYY-MM-DD`, accepts an optional `dueTime` in `HH:mm`, and stores a `completed` boolean. Task dates are required even when task times are omitted. Task data is stored under the authenticated account's `user_id`; legacy schedule rows default to `type:"schedule"`. Task writes and bulk sync exclude tasks from Google Calendar even if a client sends `autoSync:true`.
- `GET /api/google/events?timeMin=<RFC3339>&timeMax=<RFC3339>`: fetches existing Google Calendar events for a bounded interval (up to 93 days), including expanded recurrence instances. Results are transient and read-only in the UI, not copied into D1. Linked app-owned single events may include live Google overrides so external moves or deletions do not leave stale copies visible. Oversized or incomplete pagination returns an error instead of partial results.
- `GET /api/google/connect`: starts OAuth 2.0 authorization code flow with state and PKCE. `/api/google/callback` verifies state, exchanges the code, validates the returned ID token with Google's tokeninfo endpoint, and sets an HttpOnly session cookie.
- `POST /api/google/sync` with optional `{eventIds:[]}`: upserts events to the primary Google Calendar using a deterministic event ID. Each item reports success or failure so a partial sync is visible and safe to retry.

Refresh tokens are encrypted with AES-GCM before D1 storage. Standalone session cookies are signed, HttpOnly, Secure, and SameSite=Lax. Mutating requests validate same-origin; configure `APP_ORIGIN` exactly. Calendar event writes use a deterministic valid event ID and retry a concurrent insert conflict as PATCH, making retries duplicate-safe. A delete removes the remote event first and keeps the local record if Google cannot confirm deletion. Repeating items are stored as RRULE values. The memo parser expands multi-weekday input into individual schedule records; named or legacy circled templates provide a saved title, time, duration, and recurrence for future parses. Multiline input is validated as a whole and does not return partial events when a later line is invalid.

Google-side exception edits for individual occurrences of an app-created recurring master may not be reflected in the app's D1-generated recurrence series. Independently created Google recurrence instances are returned as read-only occurrences.

The memo parser now pairs each explicit date with its own start time before applying a shared title. For example, `10/29 10:00と11/5 14:00 ワンキャリア` returns two independently validated events with a default duration of 60 minutes each. Batches bypass AI title refinement so AI cannot collapse the events or change their temporal fields. An incomplete or invalid second pair produces a clarification without returning or storing a partial first event. Parser, API, atomic batch, and production-bundle regression tests cover this case, full-width Japanese input, reverse date order, and year boundaries. No schema changes were required for this fix.
